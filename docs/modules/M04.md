# M04 — Memory and persistence

## Published interface: `ghostlab-storage/1`

Defined in `src/ghostlab/storage/interfaces.py`. It is published first so M03
and M06 can build against one definition. It is frozen for this wave: a change
means updating this commit and rebasing the consumers, never silent drift.

| Interface | Consumer | Operations |
| --- | --- | --- |
| `MemoryStore` | M03 | `put`, `get`, `query` (scoped, effective-time and retention aware), `transition` (CAS) |
| `ApprovalStore` | M06 | `create`, `get`, `get_decision`, `record_decision` (pending → approved/rejected, digest-checked), `mark_expired`, `consume` (approved → consumed, single use) |

The interfaces follow these rules:

- **Isolation:** every call is scoped to a project taken from `TrustedScope` or
  the approval's scope. A named project that doesn't match the scope raises
  `ScopeViolation`. Another project's record reads as `NotFound`, so its
  existence isn't disclosed.
- **No policy:** stores apply atomic compare-and-set transitions. M06 decides
  approval validity and expiry, and M03 decides relevance.
- **Errors:** `StorageError`, plus `NotFound`, `ScopeViolation`, `Conflict` and
  `IntegrityError`. Messages never include record content.
- Records are M00 `ghostlab-contracts/1` models. Updated records are
  re-validated, so a transition can't bypass contract rules (for example,
  untrusted provenance can't become `verified`).

Budget reservations, artifact bytes and the workflow checkpoint saver are part
of M04's implementation for M05 and are documented below once implemented.
