## Skills and prompts

- `skills/<skill_id>.v<version>.json` holds reviewed procedures, each validated
  against `SkillSpec`. The file name must match the ID and version.
- `prompts/<prompt_version>.md` holds versioned prompt text.
- Each file's digest is the SHA-256 of its LF-normalized bytes, so a changed
  procedure or prompt shows up as a new digest while line endings don't count.
- `SkillRegistry.authorize(skill, scope)` returns a `SkillInvocation`: skill ID,
  version and digest, plus prompt version and digest. Every compiled context
  carries one.
- A skill's `allowed_tools` must be a subset of the caller's controller-issued
  `TrustedScope`; otherwise authorization raises `SkillPermissionError`. Skills
  narrow authority and never grant it.

| Skill | Role | Output schema | Status |

The compiler refuses a skill whose output schema isn't an M00 contract. The
`allow_unpublished_output_schema=True` override exists for tests only.

The repair procedure produces a suggestion for human review. Nothing in M03
executes generated code, and no procedure has tool access.

## Context selection rules (`ghostlab.context.ContextCompiler`)

The compiler is deterministic: identical inputs produce identical bundle JSON
and the same `sha256`. A bundle contains:

1. **Objective, success criteria, prerequisite refs and scope.** The controller
   supplies these. Nothing selected from memory or tools can change them.
2. **One `instruction` item.** It holds the prompt text, the skill steps, the
   stop conditions, the output schema and a fixed notice that untrusted items
   are data. It always has controller provenance, and the M00 contract rejects
   instructions from any other source.
3. **Findings.** These come from `MemoryStore.query` in the caller's project,
   with `kinds`, `statuses` (default verified + unverified), `world_version`,
   an optional `campaign_id` and `limit`, effective at `as_of`. The compiler
   re-checks project, status/kind, effective window and retention and excludes
   failures as `cross_project`, `status_or_kind` or `stale`, even if a store
   leaks them. Each record keeps its own provenance and trust; its first
   artifact evidence ref is attached. Content over 2,000 characters becomes a
   preview ending in a `[truncated: N characters; full record in memory <id>]`
   marker, and references the evidence artifact (or, without one, the memory
   record itself, which stays retrievable through `MemoryStore.get`). Previews
   happen before validation and budget selection, so a maximum-length (8,000
   character) record can never overflow the 8,000-character `ContextItem`
   limit; it is kept or dropped as `token_budget` like any other item.
4. **Conflicts.** When two selected records cite the same evidence ref with
   different content (and neither supersedes the other), both stay and a
   controller `question` item names the disagreement.
5. **Observations.** Tool results always become untrusted `observation` items.
   Only the newest `max_observations` are kept, and older ones are reported as
   `not_recent`. Text over 2,000 characters is cut to a preview, which requires
   an artifact ref; an oversized observation without one is refused.
6. **Summaries.** `summarize_findings` builds a fixed template from verifier
   findings only. It cites every finding ID and returns the matching refs. No
   model text and no reasoning trace is stored or reconstructed.
7. **Budget.** Items are kept first-fit in this priority order:
   - the instruction, which must fit, or the compile is refused;
   - questions and conflicts;
   - summaries and trusted or verified findings;
   - observations, newest first;
   - unverified findings.

   Anything that doesn't fit is reported as `token_budget`.

**Token estimation:** `ceil(UTF-8 bytes / 4)` per text, plus 8 tokens per item
and 32 per bundle. It is a deterministic budgeting heuristic, not a provider
tokenizer; M01 reports actual usage.

The tests cover:

- the Explorer gets the 5 newest relevant findings out of 35 records of project
  history;
- a leaky store's cross-project, contradicted, expired, future and ended
  records are excluded;
- the store refuses another project's queries and reads;
- budget priority, dropping and refusal;
- only recent observations are kept;
- conflicts stay visible;
- injected "SYSTEM OVERRIDE" text in tool results and model-written memory stays
  untrusted data, scope is unchanged, and the contract rejects tool text as an
  instruction;
- large outputs go by artifact ref;
- deterministic digests, and a prompt change produces a new digest;
- unpublished output schemas are refused;
- a role/scope mismatch is refused;
- summary evidence stays retrievable;
- registry rules: subset-only tools, version selection, CRLF-stable digests,
  and refusal of invalid, misnamed, unknown-field, duplicate or prompt-less
  skills.

  the same cases as `tests/context/m03_fakes.py`.

## Gaps

- No live model has seen these bundles, so prompt quality and actual token
  counts are unmeasured.
- Conflict detection is structural (same cited evidence, different text). It
  does not detect semantic contradictions that cite different evidence.
- Bundles are not yet produced by M05 or rendered for a provider by M01.
- Skill and prompt files rely on code-level LF normalization for stable digests.
  An M00 `.gitattributes` entry for `skills/` and `prompts/` would make
  checkouts byte-stable too.
