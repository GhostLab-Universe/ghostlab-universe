## What downstream modules can rely on

Contract set **`ghostlab-contracts/1.1`**: the 30 set-1 contracts, version 1 and frozen, plus 17 additive world-pack and Analyst contracts (see below).
A shape change needs a new version and an interface proposal to M00.

- **Source:** strict Pydantic v2 models in `src/ghostlab/contracts/`
  (`strict=True`, `extra="forbid"`, `frozen=True`).
- **Published canonical form:** `schemas/v1/<name>.schema.json` (JSON Schema
  2020-12, `$id` = `urn:ghostlab:contract:<name>:1`), `schemas/v1/index.json`
  (names, versions, producers, consumers, schema digests) and
  `schemas/v1/contracts.bundle.json` (all definitions together).
- **Frontend types:** `schemas/typescript/contracts.ts`, generated from the bundle.
  It is not a second source of truth. Do not edit it by hand.
- **Examples:** `examples/contracts/<name>.<variant>.json` (hand-authored test
  fixtures) and `examples/contracts/core/*.json` (regenerated by executing the
  synthetic refund core). See `examples/contracts/README.md`.

Rules encoded in every contract:

- Unknown fields fail at every nesting level.
- Statuses are closed string literals.
- Money is integer minor units. Booleans, floats, strings and negatives fail.
- Identifiers, digests (`sha256` lowercase hex), W3C trace/span IDs and RFC 3339
  UTC timestamps (`...Z`) are pattern-checked.
- Nullable fields are required and must be sent as `null`, never omitted. This
  keeps model-facing schemas within Meta's documented strict-output restrictions.
- Validate wire data with `model_validate_json`. Python-mode `model_validate`
  behaves the same for these contracts, because no field uses `datetime`, `Enum`
  or tuples.
- Validated models are immutable all the way down. Lists and dicts, including
  JSON blobs such as tool arguments, become read-only `FrozenList`/`FrozenDict`
  subclasses, so they still serialize, deep-copy and pickle normally.
  `model_dump()` returns plain, independent copies. `model_construct` and
  `model_copy(update=...)` skip validation and freezing, so don't use them on
  untrusted data. `TASK_TRANSITIONS` is read-only too.
- `schema_version` must be the JSON integer `1`, and `stream` the JSON boolean
  `false`. `true`, `1.0`, `0` and `"1"` fail. A generic JSON Schema validator
  still treats `1.0` as the integer `1`, so the Python contracts are the
  stricter reference.
- Cost amounts and currencies are set together or both left `null`, in
  `BudgetLimits`, `BudgetUsage` and `Usage`.

### Trusted identity and scope

Identity and authority come only from the controller or the session:

- `TrustedScope.issued_by` is the literal `"controller"`.
- `CampaignSpec`, `ApprovalSubmission`, `ModelReply`, `ProposedToolCall` and
  `ExperimentProposal` have no principal, project or scope field. Tests confirm
  that an injected `principal`, `scope` or `actor_id` is rejected.
- `Provenance` forces `tool_result` and `model_output` sources to
  `trust: "untrusted"`.

These are shape guarantees only. Authorization stays in M06 and in the world.

### v1 capsule compatibility

`capsule_v1` models today's format exactly; no v2 is introduced. Tests confirm:

- A capsule exported by the unchanged core validates.
- A capsule re-serialized through the contract still loads, and
  `ghostlab.capsule.replay` reproduces it with `model_calls: 0`.
- The published example capsule replays.

Any v2 belongs to M02, with migration tests against these fixtures.

### Consuming the contracts

- **Python:** install the `contracts` extra (or `service`) and
  `from ghostlab.contracts import ...`. `ghostlab.core`, `capsule` and `cli` never
  import it; a test enforces this.
- **TypeScript (M08):** `import type { RunResult } from "../../schemas/typescript/contracts"`.
  `web/vite.config.ts` is M08's, so M08 adds `server.fs.allow: [".."]` if the
  dev server needs files outside `web/`.
- **After changing a model:** run `python -m ghostlab.contracts.export`, then
  `npm --prefix web run contracts:generate`. Pytest fails on Python schema and
  example drift. TypeScript drift (`contracts:verify`) and the example type
  check (`contracts:typecheck`) run only when invoked. There is no CI yet: M09
  owns `.github/workflows/` and should wire in pytest, `export --check`,
  `uv lock --check` and both npm scripts as required checks.

### World packs: a reviewed, closed set

`src/ghostlab/contracts/world_packs.py` registers each world's manifest
(`world_pack/1`). A manifest lists the world's tools (each with an effect
kind), its injectable faults (each tied to a shared fault pack), its
deterministic invariants, its checked-in adapters and its replay dispatch.
`world_version` is a `Literal` over the registered packs, so a world can't be
named with a free string. Every generic contract checks tool, fault,
invariant and adapter names against the pack for its `world_version`.

### Refund mapping (lossless)

`ghostlab.contracts.world_refund` converts refund v1 runs, scenarios,
proposals, diffs, findings and capsules to the generic forms. Runs,
scenarios, proposals and capsules also convert back. Tests confirm:

- `run → generic → run` is identical;
- `capsule_v1 → capsule_v2 → capsule_v1` is identical, including the checksum,
  and the result still replays with 0 model calls.
- Conversion verifies the incoming checksum in both directions and never
  replaces it. A payload edited without updating its checksum, or a placeholder
  checksum, raises `CapsuleChecksumError`. Conversion can't launder a corrupted
  capsule into one that loads.

The refund core keeps emitting v1. `ghostlab.capsule` (owned by M02) is
unchanged.

### Promotion of `group-journey/1` (2026-10-30)

This promotion is stacked on M02's journey implementation (PR #10). It changes
no schema, contract name or contract set version.

- **Registry.** The status is now `implemented`, so `is_executable()` is true,
  and the manifest is frozen. "Frozen" is a review policy, not a digest pin:
  `test_pack_manifests_are_published_and_fixed` only checks that the published
  `world_pack.*.json` matches the registry. Any change therefore shows up as a
  diff in a published example, and review must refuse it without a new world
  version. The same is true of `refund-world/1`. Two text fields changed before the freeze:
  - The `journey-version-checked` description said "re-reads intent version
    and permissions before each commitment". The adapter actually re-reads
    the version once before confirming, and permission before each delivery.
    The description now says that.
  - `source` names the engine, as the refund pack's does.
- **Generated evidence.** `export` now runs M02's engine to produce
  `world_run_result.journey_fixture`, `world_reality_diff.journey_fixture`,
  `world_invariant_finding.journey_revoked_delivery` and
  `capsule_v2.journey_fixture`, the same way it produces the refund examples.
  They live in `examples/contracts/core/` and replace the hand-written
  placeholders, which have been deleted. The placeholder capsule claimed to be
  "not executable yet", and its run had a made-up state shape. The published
  capsule now replays as reproduced, with 0 model calls.
- **Corrected examples.** Once the world could run, the 1.1 journey example
  scenario turned out not to test its own proposal. The proposal predicts
  that "a message queued before revocation is still delivered afterwards".
  But the scenario revoked sharing from event 5, before anything was queued
  (events 7–9), and it also injected stale memory. As a result, the naive run
  broke all three invariants instead of the predicted one.

  The scenario and proposal now use the revocation fault at its default
  trigger: sharing is revoked from the event after the viewer's message is
  queued. The naive run then violates exactly `delivered_messages_permitted`,
  at event 12. The tool invocation, tool result and evidence interpretation
  examples now cite that event and message (`msg-3`) instead of event 3.
- **Tests.** The executability and walk assertions now expect journey to be
  executable. The two scenario-type mutations target the single remaining
  fault. Two new tests check that the published journey capsule replays, and
  that every journey example cites the recorded delivery and the revocation
  that followed queueing.
- **Rejected alternatives:**
  - *Keep the placeholders.* They describe evidence the engine can't produce.
  - *Generate the examples under new names.* That would churn about 20 test
    references for no gain; the `ex()` lookup already falls back to `core/`.
  - *Keep the old scenario and loosen the walk test.* That would publish an
    example that doesn't test its own hypothesis.
- **Still open:** M05 and M06 don't consult `is_executable()` yet, and they
  accept only refund campaigns. Running journey campaigns through the
  controller remains their follow-up.
- **Validation** (2026-10-30, Windows 11, CPython 3.13.18, uv 0.13.6, Node
  24.22.1). This ran on a fresh clone with empty uv and npm caches, at code head
  `8f9c23a`. That head merges M02 `8a6e9bd`, which includes all three review
  rounds' fixes, and the integration base is `774165a`. The calendar log rows
  now hold the scheduled window, the reservation, and separate participant and
  entry IDs, with no joined label, so the generated journey examples were
  regenerated; the cited evidence is unchanged (event 12, `msg-3`):
  - `uv lock --check`: consistent;
  - pytest: 1140 passed, 6 subtests (1085 before the M02 review fixes);
  - `export --check`: no drift;
  - bare core: 14 tests OK;
  - refund demo: 250000 / 500000 / 250000, divergence at event 2, and replay
    reproduced;
  - `journey-demo` and `journey-replay`: 0 model calls, and replay reproduced;
  - `npm ci`, then `contracts:verify` (`contracts.ts` matches the bundle) and
    `contracts:typecheck` (`tsc` 7.0.2 strict, every example): both OK.

### Promotion of `service-relay/1` (2026-10-30)

This promotion is stacked on M02's relay implementation (`feature/m02-service-relay`).
It changes no schema, contract name or contract set version.

- **Registry.** The status is now `implemented`, so `is_executable()` is true, and the
  manifest is frozen under the same review policy as the other two packs. The shapes
  didn't change: tools, arguments, effects, fault ids and parameters, invariant names
  and adapter ids are all as specified, and M02's manifest test passed against them
  before this promotion.
- **Text corrected before the freeze.** Each of these said something the engine
  doesn't do:

  | Field | It said | It now says | Why |
  | --- | --- | --- | --- |
  | `inspect_availability` | slots, parts and current leases | also the promise version and who holds the conversation | The adapters depend on those two |
  | `stale_availability_competition` | competing jobs see stale availability | they take resources while the counters stay stale; the lease list stays true | The lease list staying true is what makes the fault fair to a careful agent |
  | `competing_jobs` | jobs that read the same stale availability | competing jobs that take a free resource | That is what the number counts |
  | `lost_reservation_ack` | ...and is retried | whether to retry, and under which key, is the adapter's choice | The fault loses an acknowledgement; retrying is the behaviour under test |
  | `takeover_with_queued_confirmation` | while a confirmation is queued | the first job's conversation, once its leases are in place, while the confirmation is pending | The world has no queue, and the fault has no parameter naming a conversation |
  | `allocations_within_capacity` | never exceed capacity or duplicate ownership | no lease, at its grant, does so | The verdict is taken at the grant, so a later release erases nothing |
  | `confirmations_backed_by_reservations` | has valid matching reservations and promise versions | the version in force at its event, kept to the end | It is checked at both points |
  | `no_automation_after_takeover` | until explicitly resumed | from the event the owner holds it; no tool gives it back | Nothing in this version resumes automation |
  | `relay-lease-checked` | checks ... before acting | plans from the lease list and re-reads before confirming | It says which check happens when |
  | `source` | the design plan | the engine, as the other packs do | |

  The fault id `takeover_with_queued_confirmation` still says "queued". Ids are shape,
  and renaming it would have churned every reference for no change in behaviour.
- **Generated evidence.** `export` now runs M02's engine to produce
  `world_run_result.relay_fixture`, `world_reality_diff.relay_fixture`,
  `world_invariant_finding.relay_automation_after_takeover`,
  `world_scenario.relay_takeover`, `world_experiment_proposal.relay_takeover` and
  `capsule_v2.relay_fixture`, in `examples/contracts/core/`. All describe one run: the
  local-success adapter confirms `job-1` at event 4, the event the owner's takeover
  lands on. The scenario caps the run at 20 tool calls, so unlike the published journey
  scenario it is also a runnable proposal. There were no relay placeholders to replace.
- **Tests.** The executability assertion now expects relay to be executable. The gate
  tests that used relay as the specified pack (M00, M06 and M05) now mark a pack
  specified with a monkeypatched registry, so promotion removed no gate coverage. New
  tests check that the published capsule replays and that every relay example describes
  the same recorded failure, and the name-validation table covers relay.
- **Rejected alternatives:**
  - *Rename the takeover fault.* See above.
  - *Add a resume tool or a conversation parameter.* Either is a behaviour change, and
    this promotion records what exists.
  - *Generate only the four evidence examples, as journey did.* The scenario and
    proposal are then hand-written and can drift from the run they describe.
