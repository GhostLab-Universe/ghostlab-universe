## Telemetry interface

Standard library only, so importing it loads no Pydantic, httpx or LangGraph (tested in a
subprocess). M09 instruments no other package: each owner injects a `Telemetry` and
writes against it. `NULL_TELEMETRY` is a safe default that records nothing.

```python
telemetry = Telemetry(FileSink(path, max_bytes=8_000_000), clock=clock)
context = TraceContext(trace_id=state["trace_id"], project_id=project, campaign_id=campaign,
                       versions=Versions(workflow_version="ghostlab-orchestration/2"))
with telemetry.span("model.call", context.with_task(task_id), role="explorer") as span:
    span.usage = Usage.from_mapping(reply["usage"])  # a missing value stays None
    span.attempt, span.outcome = 1, reply["status"]
telemetry.event("approval.requested", context, approval_id=approval_id,
                approval_status="pending")
```

Use the campaign's own `trace_id`, which is stable across a restart. The context is
passed explicitly rather than held in a context variable, because the controller runs
baseline and fork on worker threads.

### Record fields (`ghostlab-telemetry/1`)

A record is closed: `validate_record` rejects unknown fields, and a new field is a
schema change. Events and spans share one shape. `None`/`null` always means unknown or
not applicable.

| Field | Type | Meaning |
| --- | --- | --- |
| `schema` | `ghostlab-telemetry/1` | Version of this shape |
| `kind` | `event` \| `span` | A point in time, or a timed scope |
| `name` | dotted lowercase | See `EVENT_NAMES`; any matching name is accepted |
| `timestamp` | RFC 3339 UTC | When written (a span's end) |
| `started_at` | RFC 3339 UTC \| null | Spans only |
| `trace_id` | 32 hex | The campaign's W3C-shaped trace id |
| `span_id` | 16 hex | This record |
| `parent_span_id` | 16 hex \| null | Parent trace id for nesting |
| `project_id`, `campaign_id`, `task_id` | text \| null | Ownership and position |
| `role`, `provider`, `model` | text \| null | Who did the work |
| `prompt_version`, `skill_id`, `skill_version`, `workflow_version`, `world_version` | text \| null | What it ran |
| `latency_ms` | int \| null | Measured by the injected timer for spans |
| `usage` | object | `input_tokens`, `output_tokens`, `cost_minor`, `cost_currency`, each nullable |
| `attempt`, `retries` | int \| null | Retry position and count |
| `cancelled` | bool \| null | Cancellation |
| `validation_failures` | int \| null | Rejected model or tool output |
| `approval_id`, `approval_status` | text \| null | `pending`, `approved`, `rejected`, `expired`, `consumed` or `denied` |
| `outcome`, `error_code` | text \| null | Result, and M00's `ErrorCode` where there is one |
| `attributes` | flat object | Allowlisted scalars only |
| `dropped_attributes` | int | How many attributes were refused |

### What can't be recorded

Redaction is deny-by-default, on top of M06's `Redactor`, which isn't copied:

- There's no field for a prompt, reply, tool argument, customer record or free text.
  Evidence is referenced by id or digest.
- Attributes survive only if the name is in `ATTRIBUTE_ALLOWLIST` (or was added at
  construction, where a secret-looking name is refused) and the value is a scalar.
  Everything else is dropped and counted.
- Text must be identifier-shaped. Free text is replaced whole, not scrubbed. So are runs of
  24 or more letters and digits, tokens split into parts by separators, UUIDs, email
  addresses, anything written as `secret-name=value` or `secret-name:value`, and common
  credential shapes that M06's patterns don't name. A record's `name` goes through the same
  check, and one that fails it is dropped, because a name can't hold the marker.
- A sha256 digest (64 lowercase hex) stays, so **a 64-hex secret also stays**: the two can't be
  told apart. A trace id has its own validated field, so 32 hex in text counts as a key. A
  token of plain words, or a short one, looks like a name and stays too. This is a filter on
  top of a closed schema with an allowlist, not a guarantee about every possible secret.
- An exception's message is never recorded. A span records `outcome: error` and the
  exception's class name in the `error_class` attribute.
- If a record can't be sanitized, it's dropped and counted. It's never written raw.
- A failing sink, clock, timer or id generator is counted and never reaches the business
  path. A span that can't start records nothing, and the caller still gets a span to write on.
  A failure while closing never replaces the caller's exception, even with `strict=True`.

### Sinks and the export boundary

| Sink | Bound | Notes |
| --- | --- | --- |
| `InMemorySink` | `max_events` (10,000), newest kept | `dropped` counts evictions |
| `FileSink` | Each file at most `max_bytes` (8 MiB); at most `max_bytes × (backups + 1)` | JSON Lines. Checked before each write. Rotates; with `backups=0` it drops new records. `dropped` counts |
| `FanOutSink` | none of its own | One failing sink doesn't stop the others |
| `OtlpExportSink` | `max_buffer` (4,096) | Hands OTLP/JSON batches to an injected `SpanExporter` |

`to_otlp` is a pure mapping to the OTLP/JSON trace shape. There's no SDK, no exporter and
no connection. OTLP has no null, so unknown usage is omitted, never sent as 0, and
`ghostlab.usage.unknown` names what was unknown. The `gen_ai.*` attribute names follow
OpenTelemetry's GenAI conventions, which are still in development, and this mapping
hasn't been tried against a live collector.

### Retention and access

| What | Kept for | Access | Enforcement |
| --- | --- | --- | --- |
| Local telemetry files | 30 days after the last write, and at most the sink's byte bound | The operator's user account | **Byte bound: code** (`FileSink`). **Age: code, when called** (`prune_expired`); nothing schedules it yet. Moving a file out of the sink is the audit hold |
| POSIX file modes | n/a | Files `0600`, directory `0700` | **Code**, on creation |
| Windows ACLs | n/a | The directory must not grant other users access | **Documented only.** Modes don't apply on Windows; files inherit the directory's ACL |
| Telemetry across projects | n/a | A reader sees only its own `project_id` | **Documented only.** Records carry `project_id`, but no authenticated reader exists until M07 |
| In-memory records | Process lifetime, at most `max_events` | Same process | **Code** |
| Exported spans | Whatever the collector keeps | The collector's operator | **Documented only.** No exporter ships. Enabling one is a reviewed deployment change, and retention there must be recorded in that change |
| Evidence (runs, capsules, findings) | Per M04's retention, not telemetry's | Project-owned artifacts | M04 |

Telemetry is operational evidence, not the audit of record: pass or fail comes from
stored runs and verifiers, and deleting telemetry changes no verdict.

### Tracing a campaign today

No package writes telemetry yet, because each owner adds that. Until then,
`emit_campaign_trace` rebuilds a trace from `controller.state()`, plus the ledger totals
and HTTP attempts when they're available:

- It reads structured fields only. Event summaries and error messages are skipped, because
  they can quote model output.
- Every id is derived, so rebuilding a campaign from the same state gives the same records.
- Tasks, errors and HTTP attempts have no stored time, so they carry the campaign's last
  recorded time, and `latency_ms` is null. Per-call timing needs M05 and M01 to write
  spans as they run.

## Independent evaluations (`ghostlab-evaluation/1`)

```sh
python -m evals.run --out <dir>      # run, store evidence, score, gate; exit 1 blocks
python -m evals.gate <dir>           # rescore stored evidence only
python -m evals.release --evidence <dir> --commit <sha>
```

| Step | Module | Reads |
| --- | --- | --- |
| Run | `evals/cases.py`, `evals/harness.py` | Drives the real controller, M04 SQLite stores, M01 adapter, M03 context, M06 policy and M02 worlds. Only the HTTP transport is mocked, with labeled fixtures |
| Record | `evals/evidence.py` | Copies what the campaign left behind into `<dir>/evidence/<case>.json`, reading runs through the M04 artifact store, and writes a trace to `<dir>/telemetry/` |
| Judge | `evals/oracles.py` | Recomputes each verdict from stored runs. Shares no code with M02's verifiers, M06's guard or M05's findings |
| Score | `evals/score.py` | Files only. It can't reach a controller, a store or a model |
| Gate | `evals/gate.py` | Compares the report with the reviewed `evals/expected.json` |

A case's harness is separate from M05's on purpose, and the cases assert outcomes from
evidence rather than repeating M05's unit checks. Every case also gets these checks:

| Common expectation | Meaning |
| --- | --- |
| `evidence_digests_match` | Each stored run still hashes to its recorded digest |
| `every_invariant_verdict_matches_a_recomputation` | Every invariant of the world is recomputed from the stored run and compared with the run's checks. A fork or repaired run must also have a matching finding for every invariant: no findings is a failure. Baseline runs have no findings, so only their checks are compared |
| `stored_runs_are_internally_consistent` | Trace numbering, the final state equal to the last event's whole state, and the customer and order. The whole state before and after every event is compared, so a read or a refused call that changed anything fails, and a tool may change only its own fields. Logs and the ledger only grow, one row per call. Every stored refund total must equal its ledger. The one exception is a revocation, which takes effect as a call starts, so a read or denial may show exactly that: a new timeline row for this event and that participant turned off |
| `tool_ledger_matches_the_stored_runs` | The ledger charges exactly the tool calls in the runs that were kept |
| `coverage_matches_the_stored_runs` | Recorded `coverage` says what the stored runs say. For refund this is exact in both directions. For journey, a claimed fault needs evidence, and a delivery that broke permission must count as triggered; a fault with no effect isn't recomputed, because that's M05's own rule |
| `no_secret_in_stores` | Every byte of every SQLite file and artifact was searched for the fixture credential and the synthetic secret |
| `no_secret_in_evidence`, `no_secret_in_telemetry` | The same, for what the suite produced, including rotated telemetry files |
| `cited_events_match_a_recomputation` | Each failed finding cites exactly the events recomputed from the stored run, for every invariant |
| `reality_diff_matches_the_stored_runs` | The diff's violated invariants and first divergence match the stored baseline and fork. For refund its totals match the sum of each run's ledger, not the run's stored total, which is only a claim |
| `approval_events_match_the_decisions` | Events are numbered in order, and every requested or decided approval is on the record |
| `trace_valid_and_complete` | Each campaign has a valid trace from its own trace id, with one root span and one record for every event, task, error and HTTP attempt. Each record's name, campaign, task, role, world, outcome, error code, attempt, approval status and attributes must say what the evidence says, and each needs a project. Span ids and times aren't compared, because evidence doesn't hold them |

An adversarial fixture stands in for a model that obeyed the attack. Nothing here
measures how a real model behaves.

### Report shape

| Field | Meaning |
| --- | --- |
| `schema` | `ghostlab-evaluation/1` |
| `inference`, `live_provider_contacted`, `fixture_label` | Always `mocked`, `false` and the fixture label. The gate refuses anything else |
| `commit`, `dirty`, `package_path`, `code_sha256` | From `run.json`: the checkout, whether it had local changes or the run rewrote its expectations, where `ghostlab` was imported from, and a digest of the code that ran |
| `origin_verified` | Always `false`. Nothing is signed. The gate refuses anything else |
| `environment` | Python version and platform |
| `aggregate` | Totals, plus `by_category`. Each rate carries its numerator and denominator |
| `cases[]` | `case_id`, `category`, `world`, `status`, `failed_expectations`, `expectations`, `metrics`, `telemetry_records`, `local_wall_ms`, `fingerprint` |
| `deferred[]` | What wasn't measured, and why |

`fingerprint` holds everything deterministic: outcomes, task states, error codes, run
digests, finding verdicts and cited events, event kinds in order, Reality Diffs, coverage,
stored memory by status, model and tool ledger totals, HTTP statuses, measurements and
metrics. Local wall time stays out of it.

| Metric | Definition |
| --- | --- |
| Tool success | Trace events without an error, over all events. An injected fault or a guard denial counts as a failure, and both are also reported separately |
| Handoff failures | Tasks with a dependency that ended skipped, failed or cancelled, over all tasks with one |
| Recovery | Recoveries that reached the required result, over recoveries attempted |
| Human correction | Approval decisions recorded, how many were rejections, and how many are still pending |
| Latency | `provider_ms` is null, because no provider was contacted. `local_wall_ms` is this machine running fixtures |
| Cost per successful task | Null. No price is verified, and the ledger records no cost |
| Fixture tokens | Ledger totals of fixture usage (700 in, 120 out per reply). They describe the fixture, not a model |

The random, one-pass and adaptive comparison is **deferred**. Inference is scripted, so
there's nothing to sample, and no result is claimed.

to 0.13.6, and actions are pinned to the commits their release tags pointed to on

**This workflow has not run on GitHub.** Not verified:

- that GitHub accepts the file, or that the pinned actions run as written;
- that evaluation digests match on Linux, where they should be identical because they're
  computed from canonical JSON, though that's unproven until the first run;
- the `core-bare` step on a runner (it passed locally with uv 0.13.6 on Windows);
- that `promotion-gate` actually blocks anything. It must be made a required status check
  by a repository admin, and until then the block is procedural.

## Release evidence

- [deploy/release-checklist.md](../../deploy/release-checklist.md): what must hold before
  promotion, and how to roll back.
- [deploy/recovery-drill.md](../../deploy/recovery-drill.md): store backup and restore,
  automated as `ops.recovery_drill`.
- [deploy/release-targets.json](../../deploy/release-targets.json): the explicit targets
  and the three separate statuses.

`python -m evals.release` builds a `ghostlab-release/1` record and exits non-zero unless
it's promotable. It deploys nothing. It takes the evidence directory and a commit: the
evidence is rescored, the stored `report.json` and the seal in `run.json` must match, and
it must come from that commit on a clean tree. The code digest is recomputed from the
commit's objects, so code imported from elsewhere can't claim a clean commit. Expectations,
targets, lock digests, the compatibility report and security gate evidence come from the
commit too, never the working tree. The record holds `expected_sha256`, plus
`live_evidence.compatibility_report_sha256` and `security_gate_evidence_sha256`, each the
sha256 of the committed bytes (null when the commit doesn't hold that file). `report_sha256`
hashes the file's bytes. `evals.run` refuses a used `--out`, `--only` that matches nothing
blocks, and a run that rewrites its expectations is stamped dirty, so it can't be released.

**A candidate is promotable only after it reaches its target branch.** The commit must be
reachable from `refs/remotes/origin/<release_target.branch>`, a missing ref blocks, and the
record's `target_ref` says which ref was used, where it pointed and whether it contains the
candidate. That ref is local state, so fetch first. A ref that's behind refuses a candidate
merged since, and one that predates a force-push can still contain a candidate the branch no
longer has. Anyone with the repository can move it, so it proves sequence, not origin. The
rollback commit must exist and be an ancestor of the candidate.

**Nothing here is signed.** The seal in `run.json` is one digest over the evidence and
telemetry files and the `commit`, `dirty`, `package_path`, `code_sha256` and
`origin_verified` fields, so an edit of a file or a field is caught. It's an accident check,
not an attestation: anyone who can write these files can run the same function and write a
matching seal, and no digest here says who produced anything. Every record says
`origin_verified: false` for that reason. See `evals/identity.py`.

**Third-party packages aren't bound to the evidence.** The record's lock digests say what the
commit pins. Nothing checks what was installed when the evidence ran, so
`dependency.installed_packages_verified` is `false`. The code digest covers this repository's
code only.

| Target | Value |
| --- | --- |
| Release | `architecture-and-refund-core`, local single-user, at the reviewed merge head |
| Rollback | `architecture-and-refund-core` at `24942bd`, **with the pre-upgrade store backup restored**. Migration 0003 is forward-only and that commit's code refuses a newer database |

| Status | Value | What can change it |
| --- | --- | --- |
| Runtime | Local development only | M07, then hosted checks |
| Dependency | Locked | A reviewed M00 change |
| Live capability | Not started | A sanitized live M01 report. A claim of `passed` isn't believed: `live_evidence.shape_checks_passed` says only that a committed file has the right shape, and `live_evidence.proven` is always false |

`promotable` is about offline promotion only. Customer-connected use is decided
separately, and a status in the targets file is treated as a claim:

| Needed for `customer_connected_use_allowed` | Why |
| --- | --- |
| `release_target.kind` is `customer_connected` | A local target is always false, whatever else the record says |
| Runtime status `authenticated_service` | No authenticated service exists yet |
| Every gate in `security_gates`, gates 1 to 4 of `docs/acceptance-gates.md`, marked `passed` with a non-empty evidence file in the candidate commit | A gate's file proves only that evidence was named; a human still reviews it |
| A documented provider, endpoint and model, accepted by the real `ProviderConfig` | Refuses an invented provider or model, plain http and an undocumented endpoint |
| A compatibility report in the candidate commit that passes `LiveInferenceAuthorization.check` | The same check the controller applies before a paid call, bound to the claimed provider, endpoint, model and spending cap, and run for every runnable world's output schema. A file only in the working tree, gitignored or not, doesn't count |
| Real calls, and the AGENTS.md limits probed | `calls_made` and `http_attempts` above 0, `probed_limits` naming timeout, cancel, rate limit and budgets, none of them in `not_probed`, and no secret in the report |
| No offline blocker | A release that can't be promoted can't be connected |

**`customer_connected_use_allowed` is false, unconditionally.** Every requirement above can
be met by typing files, so meeting them proves nothing yet. The record says why in
`customer_connected_why_not`, and the requirements stay listed as blockers. Turning it on is
a code change, and needs evidence of verifiable origin. Today's probe wouldn't qualify
regardless: `scripts/probe_provider.py` lists timeout, cancel and rate-limit handling under
`not_probed`, reports no budget probe and writes no `structured_schemas`.

No field reads as proven while origin can't be verified. `live_evidence` holds
`shape_checks_passed`, its `problems`, the report's digest, `proven: false` and
`why_not_proven`, which is the same reason as `customer_connected_why_not`.
`customer_connected_blockers` lists what's missing. A live claim doesn't affect
`promotable`, in either direction.

The gate also reads each case's `status` and expectations, recounts the aggregate, enforces
the fixture label and `origin_verified: false`, and refuses a report with no cases or a gate
with no reviewed expectations.

A regression blocks in three places, all tested: `evals.run` and `evals.gate` exit 1,
`build_record` returns `promotable: false`, and the CI job fails. Mutation tests also break real
behaviour instead of editing a file, for example sending the repaired adapter back to
retrying, running the repair unguarded, or dropping findings or memory. All are caught.
