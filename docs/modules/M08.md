# M08 — Guided refund run: UI, developer guide, browser acceptance (Track D)

Status: **service-first; fixture path is dev-only.** Track D shipped fixture-mode complete;
the `dashboard-live-wiring` pass rewired the production path onto the live E4 service
(`web/src/api.ts` transport, owned by the parallel track) with reference capture,
server-derived provenance, and gap coverage for qualify/cancel/compare/export/recovery.
Base: `feature/m00-foundation` (shared checkout; Track D ran in parallel with Tracks A/B/C).
This module owns `web/src/`, `web/public/`, `web/tests/`, `web/index.html`,
`web/vite.config.ts`, `web/tsconfig.app.json` and this guide. It does not edit backend
packages, canonical schemas, manifests or lockfiles: `web/package.json` is untouched

Prior capability/contract refs for this track arrived as gaps, so the build is grounded in
inspected repo sources instead: `src/ghostlab/core.py`, `src/ghostlab/capsule.py`,
`src/ghostlab/envs/*` return shapes, `schemas/v1/*`, `schemas/typescript/contracts.ts` and
`examples/contracts/**`. No M07 route contract is invented anywhere in this module.

## What was built

A 7-step guided flow over the synthetic INR refund world. Every step is a real route served
from the production bundle:

| Step | Route | Purpose |
| --- | --- | --- |
| 1 | `/guide/1-environment` | Select env, import + digest a v1 manifest |
| 2 | `/guide/2-qualification` | Inspect capabilities, qualification, env limits |
| 3 | `/guide/3-agent` | Select vulnerable/repaired adapter + operator note |
| 4 | `/guide/4-configure` | Fixture, faults, invariant focus, limits, objective |
| 5 | `/guide/5-review` | Effective config, provenance, derived payloads |
| 6 | `/guide/6-run` | Run, recorded config, evidence, Reality Diff |
| 7 | `/guide/7-export` | Export bundle, compare, retest |

`/` redirects to step 1; unknown routes render a NotFound screen. State is in-memory:
in-app navigation preserves it, full page loads reset to defaults (both covered by tests).

### One server-validated config

`web/src/config.ts` (pure, zero imports) defines `EffectiveConfig` plus the validation the UI
applies before running and the API client re-applies on submit — the same rules the service
will enforce. No displayed control is complete until its value reaches execution and is
recorded: each of the 20 `CONTROL_PATHS` renders in the step-5 provenance table, is echoed in
the step-6 recorded config, and ships in the step-7 export. The browser suite asserts this
chain for values it sets (25 tool calls, repaired adapter, edited objective, edited fixture,
removed invariant, imported digest).

Constraint sources (mirrored, never forked):

| Config area | Mirrors |
| --- | --- |
| fixture bounds, scenario bounds, adapter behavior | `src/ghostlab/core.py` |
| budget/objective/criteria bounds, payload shapes | `schemas/v1/campaign_spec.schema.json`, `budget_limits.schema.json`, `experiment_proposal.schema.json` |
| env id/version/tool/hook patterns, manifest v1 rules, canonical digest | `src/ghostlab/envs/registry.py`, `manifest.py` |
| rendered result/diff/capsule/finding types | `schemas/typescript/contracts.ts` (`RunResult`, `ExperimentResult`, `RealityDiff`, `CapsuleV1`, `InvariantFinding`) |

`toCampaignSpec`/`toExperimentProposal` map the config onto the frozen payload shapes; the
proposal text is derived deterministically from the config (no model output at this stage).

### Fixture tiers (never mixed silently)

- **Approved M00 fixtures** (`examples/contracts/**`, incl. `core/`): validated by
  `tests/contracts/test_contracts.py`. Rendered only beside
  "Approved M00 fixture: development aid, not evidence from this run."
- **Illustrative env fixtures** (`web/src/fixtures.ts` + `illustrative-manifest.json`):
  hand-shaped from the inspected Track A return shapes to preview UI states. Rendered only
  beside "Illustrative dev aid … never evidence."
- **Scripted runs**: step 6 records the submitted config but shows fixture results, labeled
  "Scripted run…". The frontend never computes financial verdicts; checks come from evidence.

### Service-first production path (`dashboard-live-wiring`)

The production bundle instantiates `ServiceGuideApi` (`web/src/serviceClient.ts`), which
delegates the core flows to `LiveExperimentApi` (`web/src/api.ts`, implemented by the
parallel E4 track against the real `/v1/*` routes) and never falls back to fixtures: a
dead service surfaces a typed connection error with the config preserved for retry.

- **One transport**: every route call for envs/capabilities/report/import/submit/runs/poll
  lives in `web/src/api.ts`. `serviceClient.ts` only calls the routes the transport does
  not: qualify, cancel, compare, export and standalone group reads (reload recovery). If
  the parallel track extends the transport, the gap calls here fold into it.
- **Reference capture**: the transport returns assembled evidence but drops the
  service-issued ids, so the adapter observes the fetch traffic of each delegated call
  (scoped wrapper, restored afterwards) and records requested/resolved/group/run ids,
  mapping notes and pins. No extra requests, no invented ids, no duplicate execution.
- **Honest assembly**: provenance labels derive from observed pins + run bodies
  (deterministic-adapter only when the controller recorded 0 model calls; no paid calls
  because the contract has no model/cost path). The diff/finding/capsule the transport
  assembles in the browser from executed evidence are labeled browser-assembled;
  a server-issued finding/capsule is not part of this contract.
- **Dev-only fixtures**: `?fixture=1` loads `FixtureExperimentApi` via dynamic import,
  gated on `import.meta.env.DEV`. Production builds eliminate the branch, so no fixture
  chunk is emitted; `?fixture=1` in a production build shows an explicit refusal.
  The browser suite forbids `FixtureExperimentApi`, `fixture-scripted` and `Scripted run`
  in every emitted chunk.
- **Control-to-execution audit**: `CONTROL_DISPOSITIONS` (`web/src/config.ts`) marks
  every leaf execution-affecting, recorded-metadata or unsupported, mirroring the
  submit mapping notes (the runtime drift detector). Unsupported limits
  (model/token/parallel/cost) are disabled in step 4 at their only honest value
  (0/1/null) and coerced on visit, so the service can only record honest metadata.
- **Reload recovery**: run handles persist to sessionStorage; a fresh load re-reads the
  groups via the API, digest-verifies them, and restores the newest verified run as
  historical evidence. Group handles are in-memory server-side, so a server restart
  expires them honestly (stored SQLite runs survive, handles do not).

## Commands (service-first pass executed 2026-11-03 on Windows 11, Node v22.14.0)

> Note: `web/package.json` engines ask for Node >=24.22.1 <25 (M00's supported set). The
> commands below also pass on the installed Node v22.14.0; that is an observation, not a
> support claim — M00 owns the engines range.

From the repository root unless noted:

```sh
# 1. Typecheck the guided UI (strict + exactOptionalPropertyTypes +
#    noUncheckedIndexedAccess). Exit 0.
web\node_modules\.bin\tsc -p web\tsconfig.app.json --noEmit

# 2. Unit tests (stock Node type stripping). 16 config-core + 29 service
#    adapter tests pass; oracles are node:crypto, a python-stdlib
#    canonical-JSON one-liner, and stubbed service traffic.
node --experimental-strip-types --test web/tests/config.test.mjs web/tests/serviceClient.test.mjs

# 3. Production build (run with cwd=web). Single chunk — the fixture path
#    is eliminated, verified by the bundle scan in step 4.
#    (PowerShell: cd web; node node_modules/vite/bin/vite.js build)
node node_modules/vite/bin/vite.js build

# 4a. Browser acceptance, dead-service mode (headless Chrome via CDP, stdlib
#     only; temp state under os.tmpdir()/track-d-accept-*, per-step PNGs).
#     /v1 is refused so the suite asserts connection-error states with the
#     config preserved — fixtures must never appear.
node web/tests/acceptance.mjs

# 4b. Browser acceptance, live-service mode. Start the E4 service with
#     private temp databases, register the refund env (the suite qualifies
#     it through the UI), then run the suite against it (the suite proxies
#     same-origin /v1 to it, so no browser CORS is involved). 88/88 passing
#     2026-11-03. Restart the service whenever the databases are reset
#     (schema is ensured at startup); never run two suites against one
#     store (identical configs collide on attempt 0 — see "Open gaps").
$env:GHOSTLAB_REGISTRY_DB="$env:TEMP\gl-accept-reg.sqlite"
$env:GHOSTLAB_STORE_DB="$env:TEMP\gl-accept-store.sqlite"
$env:PYTHONPATH='src'
python -m ghostlab.envs env-register --db "$env:TEMP\gl-accept-reg.sqlite" `
  --env-id refund-env --env-version refund-env/1 `
  --adapter-ref ghostlab.envs.adapters:RefundEnvAdapter --display-name "Synthetic refund" `
  --tools '[{"name":"get_order","parameters":["order_id","customer_id"]}, {"name":"get_refund_status","parameters":["order_id","customer_id","idempotency_key"]}, {"name":"issue_refund","parameters":["order_id","customer_id","amount_minor","idempotency_key"]}]' `
  --modes '["recorded-actions","deterministic-reset"]'
python -m uvicorn ghostlab.api.app:create_app --factory --host 127.0.0.1 --port 8917
node web/tests/acceptance.mjs --service=http://127.0.0.1:8917

# 5. Existing workflows still pass (untouched by this module).
npm --prefix web run contracts:verify        # contracts.ts matches bundle
npm --prefix web run contracts:typecheck     # exit 0
$env:PYTHONPATH='src'; python -m unittest tests.test_core            # 14 OK
$env:PYTHONPATH='src'; python -m ghostlab replay examples/contracts/core/capsule_v1.refund_failure.json
# reproduced: true, model_calls: 0
```

## Open gaps and requests

- **M00 requests**: pin `@vitejs/plugin-react` + `@types/react` (then delete
  `web/src/react-shim.d.ts`); decide browser-test tooling (current suite is stdlib CDP, no
  new deps); confirm whether Node 22 support matters or engines stay >=24.22.1.
- **Parallel-track dependencies** (reconciled, not duplicated): the E4 service
  (`src/ghostlab/api/*`), the `LiveExperimentApi` transport (`web/src/api.ts`), and the
  booking/fidelity/proxy/minimize examples stay owned by the parallel track — this branch
  consumes them read-only. If the parallel track extends the transport to cover qualify,
  cancel, compare, export or group reads, fold the gap calls in `serviceClient.ts` into
  `web/src/api.ts` and delegate. A server-issued finding/capsule is not part of the E4
  contract; the UI labels the browser-assembled ones until the contract grows them.
- **Known E4 limitation (verified 2026-11-03, pending on the service)**:
  `POST /v1/runs` takes only `{resolved_id}` and the worker always records
  repetition 0 / attempt 0, so re-running an *identical* config fails with
  "attempt 0 of repetition 0 is already recorded" (group failed). The UI shows
  a targeted hint for that failure; the step-7 retest suffixes the objective
  name (recorded metadata only — execution fields identical) so the service
  issues new ids; the acceptance suite uses a distinct objective per re-run.
  Proper new-attempt support on the run route is pending. Related: swapping
  database files under a running server breaks the store (schema is ensured at
  startup) — restart the service whenever the acceptance databases are reset;
  editing adapter sources invalidates existing registrations by design
  (re-register, re-qualify, re-resolve).
- Fixture-mode limits: dev-only `?fixture=1` under `vite dev`; production builds cannot
  reach fixtures. Canonical-JSON vs Python is verified on the ASCII illustrative
  manifest (non-ASCII `ensure_ascii` path untested).
