# M07 — Authenticated control plane

Interface published: `ghostlab-api/1` (`src/ghostlab/api/`).

Base: `feature/m05-world-campaigns`, branched at `4501fa4` and merged forward to
`3174a03` (PR #17). That carries `architecture-and-refund-core` at `9f919f1`, with #14,
#15 and #16 merged. #17 itself is unmerged; contract-first development against it was
explicitly authorized.

It consumes these interfaces:

| Interface | From | Used for |
| --- | --- | --- |
| `ghostlab-contracts/1.1` | M00 | Every record, run, diff, finding, approval, event and error |
| `ghostlab-orchestration/2` | M05 | `CampaignController`: start, resume, recover, state, record, capsules |
| `policy-1` | M06 | `ApprovalService`, `authorize_world`, `authorize_capability`, `ApproverAuthority`, `require_local_dev` |
| `ghostlab-storage-artifacts/2`, `ghostlab-storage/1` | M04 | `FileArtifactStore.for_project`, `ApprovalStore`, `graph_checkpointer` |

M07 owns HTTP and session adapters. It has no scheduler, no decision logic and no
database of its own, and it reimplements no simulation.

## Endpoints

`src/ghostlab/api/openapi.v1.json` is the contract. Regenerate it with
`python -m ghostlab.api.openapi`; `--check` and a test fail on drift.

| Method | Path | Purpose |
| --- | --- | --- |
| GET | `/v1/session` | Principal, project, auth mode and inference mode resolved by the server |
| POST | `/v1/campaigns` | Create a campaign (`Idempotency-Key` required; `scripted_scenario` on a `--scripted` server) |
| GET | `/v1/campaigns/{campaign_id}` | Authoritative status; use after any reconnect |
| GET | `/v1/campaigns/{campaign_id}/events` | Poll application events (`after`, `limit` ≤ 200) |
| POST | `/v1/campaigns/{campaign_id}/cancel` | Cancel a running or stalled campaign |
| POST | `/v1/campaigns/{campaign_id}/resume` | Owner: re-check a paused campaign or continue a stalled one |
| GET | `/v1/campaigns/{campaign_id}/experiments/{experiment_id}` | Proposal, diff, findings |
| GET | `/v1/campaigns/{campaign_id}/experiments/{experiment_id}/diff` | Reality Diff with its coverage |
| GET | `/v1/campaigns/{campaign_id}/experiments/{experiment_id}/runs/{run}` | Inspect `baseline`, `fork` or `repaired` |
| POST | `/v1/campaigns/{campaign_id}/experiments/{experiment_id}/capsules/{run}` | Export a capsule |
| POST | `/v1/campaigns/{campaign_id}/experiments/{experiment_id}/capsules/{run}/replay` | Replay an exported capsule |
| POST | `/v1/capsules/import` | Validate, replay and store a `CapsuleV1` or `CapsuleV2` |
| POST | `/v1/capsules/{capsule_id}/replay` | Replay any capsule in this project (`capsule_id` is its artifact id) |
| GET | `/v1/artifacts/{artifact_id}` | Download a project artifact |
| GET | `/v1/approvals/{approval_id}` | Request, effective status, bound action, decision |
| POST | `/v1/approvals/{approval_id}/decision` | Approve or reject (`Idempotency-Key` required) |

There are no unauthenticated routes, including documentation: `docs_url`, `redoc_url`
and `openapi_url` are off.

**Shapes.** Responses compose M00 contracts. Refund evidence is mapped through
`ghostlab.contracts.world_refund`, so `WorldCampaignRecord`, `WorldRunResult`,
`WorldRealityDiff` and `WorldInvariantFinding` describe both worlds. A create body is a
`WorldCampaignSpec`, a decision body an `ApprovalSubmission`. `SessionInfo`,
`CampaignView`, `EventPage`, `ExperimentView`, `RealityDiffView`, `RunView`, `CapsuleInfo`,
`ReplayResult`, `ApprovalView` and `DecisionResult` are thin M07 views. `ReplayResult`,
`RepairView` and `Coverage` have no M00 contract yet (see requests below).

**Errors.** Every non-2xx body is `ErrorResponse`: an M00 `ErrorInfo` plus `reason`, a
stable code finer than `error.code`.

| Status | `error.code` | `reason` examples |
| --- | --- | --- |
| 401 | `unauthenticated` | |
| 403 | `forbidden` | `world_not_runnable`, `capability_denied`, `inference_not_authorized`, `approver_not_authorized`, `approver_not_allowed`, `not_loopback` |
| 404 | `not_found` | absent, or owned by someone else: identical bodies |
| 409 | `conflict` | `settings_changed`, `idempotency_key_reused`, `campaign_finished` (cancel or resume on a finished campaign), `cancel_incomplete` |
| 409 | `approval_invalid` | `digest_mismatch`, `not_pending`, `expired`, `policy_changed` |
| 413 | `validation_failed` | `too_large` |
| 422 | `validation_failed` | `invalid_request`, `capsule_invalid`, `not_a_capsule`, `secret_shaped_text`, `identifier_too_long`, `scripted_scenario_unavailable` |
| 429 | `rate_limited` | `too_many_campaigns`, with `Retry-After` |
| 500 | `internal` | generic text; detail goes only to the filtered log |

A validation error reports where and how a request failed, never the input, including
the name of an unknown field.

`settings_changed` covers every `CampaignSettingsChanged`: the current fixture differs,
a recorded fixture failed its digest, a journey campaign has none, or a scripted server
was asked to continue a campaign with no recorded scenario. The first can be fixed by
restoring the setting; the others can't. `error.message` says which.

## Outcomes

`record.status` and `outcome` reach clients exactly as M05 recorded them. Only
`repair_verified` means a repair held, and only `no_failure_found` means a finished
search found nothing.

| `record.status` | `outcome` | Meaning |
| --- | --- | --- |
| `completed` | `repair_verified` | The repair ran to the end and held. `repair.held_by` says how |
| `completed` | `no_failure_found` | Every experiment finished, every fault fired, and nothing failed |
| `completed` | `failure_found_repair_pending` | A failure was found and no repair was verified. `completed` here means the search ended, not that anything is fixed |
| `completed` | `repair_rejected` | A human rejected the repair; it did not run |
| `budget_exhausted` | `coverage_incomplete` | Nothing failed, but a run stopped at its cap or a fault never fired, so this proves nothing |
| `budget_exhausted` | `repair_incomplete` | The repair used its whole tool budget |
| `budget_exhausted` | a resource name | A budget ran out |
| `failed` | `repair_incomplete` | The repair finished without doing the task, or missed a fault the fork met (`repair.lost_faults`) |
| `failed` | `repair_did_not_hold` | A safety check failed in the repaired run |
| `failed` | `settings_changed` | The fixture changed between resume and consumption. The approval stays `approved` |
| `failed` | `no_experiment_ran` | No proposal reached execution, so nothing was tested |
| `failed` | `budget_check_failed` | The budget check itself failed, which is not an exhausted budget |
| `failed` | `approval_expired`, `approval_*` | The approval can't be used |
| `failed` | `policy_denied`, `world_not_runnable`, `explorer_failed`, `context_error`, `run_stopped` | Refused or stopped |
| `cancelled` | `cancelled_by_request` | Stopped on request |

**Coverage.** Each experiment carries `coverage` {`baseline`, `fork`, `faults_triggered`,
`complete`}, on `ExperimentSummary`, `ExperimentView` and beside the diff. It is null only
on a checkpoint older than coverage, and `faults_triggered` is null on one from before it
was recorded. `/diff` returns `RealityDiffView` rather than a bare
`WorldRealityDiff`, because a truncated run's diff shows no violations and would read as
clean. For the same reason `ReplayResult.run_status` reports what the recorded run did:
`reproduced` says only that the replay matched the recording.

**Repairs.** `RepairView` carries `run_status`, `safety_held`, `task_complete`,
`lost_faults` and, for journeys, `task_outcome`, separately. `held_by` is null unless the
repair is verified. A verified repair can have `task_complete: false`, for example when a traveller's sharing was
withdrawn; `task_outcome` says which part.

**Replay.** `ReplayResult.run_status` is what the run did, checked rather than taken from
the capsule, and null when the recording didn't reproduce, because then nothing checked it. Whether a run finished rests on a call past its cap that was never made, so
recorded requests can't show it. A recording that replays must therefore match what its
named checked-in adapter produces, in status and trace, or `capsule.py` and
`journey_capsule.py` refuse it, a 422 `capsule_invalid`. That covers a truncated run
relabelled `completed`, one with its cap raised, and a relabelled adapter. A recording that
simply doesn't reproduce is still reported as not reproduced. Honest capsules and replay
output are byte-identical to before this check. A capsule holding text shaped like a
credential, anywhere in it including dict keys, is refused with `secret_shaped_text` before
it is stored.

**Fixture.** `CampaignView.fixture_sha256` is the pinned fixture's digest, the value an
approval's `action.fixture_sha256` binds. It is null on a checkpoint with no pinned
fixture: M05 refuses to continue one, so it reads and goes no further. The fixture itself is deliberately left out of the views: it is in every
capsule's `payload.fixture`, and every recorded fact a view reports comes from the run.

## Authentication

**No production authentication exists.** `is_production_authenticated` is false for
everything, and `/v1/session` always says `production_authenticated: false`.

| Adapter | `auth_mode` | Use |
| --- | --- | --- |
| `LocalDevSessions` | `local_dev` | M06's explicit mode: `GHOSTLAB_AUTH_MODE=local_dev`, `require_local_dev` at startup, one principal of kind `local_dev` |
| `TokenSessions` | `configured_tokens` | Operator-configured bearer tokens, so more than one identity can be exercised on one machine. Only digests are kept |

Rules that hold for both, because neither is production authentication:

- `create_app` refuses `GHOSTLAB_DEPLOYMENT` other than `local`, and a non-loopback bind.
- One server per storage root. Startup takes an exclusive OS lock on `<root>/server.lock`,
  and a second holder is refused. The lock is taken where the `ControlPlane` is built, so
  `create_app`, `python -m ghostlab.api` and the fixture server all hold it. The operating
  system releases it when the process ends, so a crash can't block a restart. `create_app`
  refuses a layout whose checkpoints or stores sit outside that root (`SplitStorage`).
- No trace export. `ghostlab.api` forces LangSmith tracing off and drops its key when the
  package loads, whatever the environment says, because no destination or redaction has
  been approved. FastAPI's OTLP auto-configuration is off, and only `opentelemetry-api` is
  installed, so nothing can export.
- Every request must come from a loopback peer, with a loopback `Host` and, if present,
  a loopback `Origin`. That stops another site or a rebound DNS name from driving a
  server on `127.0.0.1`. There are no CORS headers: a browser interface reaches the API
  through a same-origin dev proxy.
- `RequestGuard` runs before routing, so a route can't be left open by forgetting a
  dependency, and a request is authenticated before its body is read or parsed.

A session resolves on the server to one principal in one project. No path, query,
header or body names a project, principal, role or scope, and the bodies forbid extra
fields. A real adapter only has to implement `SessionAdapter.authenticate`, plus
whatever replaces the loopback rule.

**Identity to world binding.** `PrincipalBinding` and `WorldActorBinding` are
trusted-host wiring in `ApiConfig.services`. `ghostlab.api.local` binds the local-dev
principal to the synthetic customer and organizer.

## Authorization

| Resource | Rule | Enforced by |
| --- | --- | --- |
| Campaigns and their evidence | Owning principal in the session's project | `CampaignController._check_owner`, on every call. Anyone else gets a 404 |
| Artifacts and capsules | Any session in the project with `read_evidence` | `authorize_capability`, then `FileArtifactStore.for_project`. The unscoped API and M05's legacy fallback are not used |
| Approvals, read | Campaign owner, or an `ApproverAuthority` approver | `ControlPlane.approval` |
| Approvals, decide | `ApprovalService.decide`, with the session as approver | M06. `approver_not_*` is a 403 before any lookup; `not_found` is a 404 for an authorized approver |

A reviewer doesn't own the campaign, so campaign routes read as absent for them. They
can read the approval's summary, risks and exact action (the digest is recomputed before
it is shown), and download the run named by `request.payload`, which is a project
artifact.

## Request identity

Identity is derived, not stored, so it survives a restart and M07 needs no table.

- **Create.** `campaign_id` is `c-` plus a digest of project, principal and
  `Idempotency-Key`. A retry finds the checkpoint and returns the **current** campaign
  with `Idempotency-Replayed: true`. A different spec under the same key is a 409. Two
  sessions' keys can't collide. Concurrent duplicates join one worker: 8 at once start 1
  campaign and send 1 model request.
- **Decide.** `decision_id` is `d-` plus a digest of project, principal, approval and key.
  A retry returns the recorded decision, even one racing the request that recorded it; a
  different decision under that key is a 409. A second key meets `not_pending`, even when
  it loses a race: M06's `conflict` is mapped to these answers and never reaches a client.
- **Capsules** are content-addressed, so export and import need no key.
- **Cancel and resume** are idempotent by state.

## Execution

`start` and `resume` are synchronous, so each moving campaign has one daemon thread
(`jobs.py`) until it pauses or finishes. It isn't a scheduler: there is no queue,
ordering or retry, and order and budgets stay with M05's graph. At most
`max_active_campaigns` (default 4) run at once. One saver is shared; `SqliteSaver`
serializes its connection under a lock. A job is registered only once its thread has
started. If the thread can't start, the request gets a retryable 503 and holds no capacity;
a decision is still recorded, reads `resumed: false` and leaves the campaign `stalled`.

**The first step.** A route waits until the controller enters its first node, or raises.
`Services.on_node` is the signal. So the controller's own gates (world, ceiling,
inference) raise a typed error to the caller with nothing stored, and a campaign is
readable the moment its id is returned. Its origin is pinned after those gates and before
its first checkpoint, so a failed pin is a retryable 500 with no campaign behind it.

**A decision resumes the campaign under its owner.** The owner comes from the approval
record, which the controller wrote from its own session. A decision can land between
the campaign reporting `awaiting_approval` and its worker reaching the pause, so the
resume then follows that worker rather than being lost. Resuming authorizes nothing:
only a stored approval and a single-use `consume` run a repair.

**Status.** A view takes `record.status` and `outcome` from one read of the checkpoint;
`record()` reads again, and a worker may have moved on in between. The job is looked up
before that read, so a worker ending during it can't read as a stall. `job.state` sits
beside the status:

| `job.state` | Meaning |
| --- | --- |
| `active` | A worker is running it |
| `idle` | Paused or finished |
| `stalled` | Unfinished, with no worker: a crash, restart or worker error, or a decided approval nothing has resumed. `job.error` holds a sanitized cause when this process saw it. `resume` continues it |

**Cancel** sets the `threading.Event` given to the controller.

| Campaign | Result |
| --- | --- |
| Running | 202; stops at the next guarded node. Journey runs also check before each tool call. In-flight HTTP isn't interrupted (M01), and a refund run finishes its run |
| Awaiting approval | 202 once it has stopped; runs the graph on to its guard, whatever the current settings |
| Stalled | 202 once it has stopped; recovers from the checkpoint with cancel set. If the interrupted step can't finish, for example its artifacts are gone, a 409 `cancel_incomplete`: the status is unchanged and `job.error` says why |
| Already cancelled | 202 |
| Otherwise finished | 409 `campaign_finished`. That includes a repair with a verdict whose only step left is writing its memory (`remember_repair`): it reads `stalled`, the cancel runs nothing, and `resume` finishes that step |

A 202 on a running campaign means a worker has the request, shown by
`job.cancel_requested`. If that worker then fails, the campaign reads `stalled` and
`job.error` starts `Cancellation did not complete`. Cancel doesn't count against
`max_active_campaigns`, because it frees capacity. A stalled campaign whose step can't
finish can't be cancelled, and `cancel_incomplete` says so. That is deliberate in M05: a
cancel set during `verify` keeps that run's evidence, so `_verify` has no guard.

M05 checks the guard before consuming, so an unused approval stays unspent, and can stay
`pending` or `approved` on a stopped campaign. Deciding it records the decision and moves
nothing: `DecisionResult` says `resumed: false` with `campaign_finished`. A cancel that
lands after `consume` leaves the approval spent and the repair unrun, which fails closed.

**Shutdown.** A server stopping is not an owner cancelling, so it never sets the cancel
flag, which would write a terminal `cancelled_by_request`. Workers get a grace period to
reach a pause or finish, then a separate signal ends them at their next node with nothing
written. Such a campaign reads as in the next paragraph.

**Restart.** Checkpoints and approvals are durable; the job registry isn't. A paused
campaign is unaffected. A campaign that was running reads `running` / `stalled` until its
owner resumes it. Nothing restarts it unasked, because a recovered node can repeat a
model call.

**Bounds.** Bodies are limited to 64 KiB, or a capsule's 2,000,000 bytes plus framing on
import, before parsing. Event pages are at most 200. Artifact reads are bounded and
digest-verified by M04.

## What leaves the server

Graph state is never returned directly: `provider`, `limits` and baselines stay inside.
Credentials stay in `ApiConfig.services`. Model text is redacted by M05 before it is
stored. M07 redacts again on the way out, with the server's own literals and for records
older than that change, and a test puts a secret directly in stored state to prove it.
Redaction is pattern-based and is defence in depth (M06). Proposal text is model output:
untrusted data, to be rendered as data. An approval's `action` isn't redacted, because it
must match its digest exactly. Run evidence comes from the synthetic world and is
returned as recorded.

**Client text is M07's.** M05 redacts what models write, so a spec's `objective` and
`success_criteria`, and a decision's `reason`, are checked here. Text that matches M06's
patterns is refused with `secret_shaped_text` before anything is stored. It is refused
rather than rewritten, so a stored spec is what the client sent and a retry still
compares equal. The patterns are broad, so ordinary text such as `token=abcd` is refused
too; the client gets a typed error and can rephrase.

## Running it

```text
GHOSTLAB_AUTH_MODE=local_dev python -m ghostlab.api --port 8787
```

One server per root. Inference is disabled there: creating a campaign is a 403
`inference_not_authorized`, and reads, capsule import and replay work.

```text
GHOSTLAB_AUTH_MODE=local_dev python -m ghostlab.api --scripted --port 8787
```

`--scripted` is an explicit opt-in, off by default and refused outside the local deployment
or off loopback. Explorer replies are checked-in proposals in `ghostlab.api.scripted`,
served through `httpx.MockTransport`: no model, no network and no key. The live-inference
gate is unchanged. Worlds, verifier, approvals, stores and capsules are the real code.

| `scripted_scenario` | Worlds | What it shows |
| --- | --- | --- |
| `default` | both | The world's failure, then a verified repair |
| `revocation_race` | journey | `journey-version-checked` leaks in lab mode: revocation after event 17, its last permission check, so the delivery at event 18 breaks the rule. The guarded boundary denies that delivery in the repair (`held_by: guarded_boundary`) |
| `fault_never_fires` | both | Two experiments whose fault never fires: `budget_exhausted` / `coverage_incomplete` |

A scenario is a closed enum on the create request. A client names one and can't supply any
proposal content; anywhere but a scripted server it is a 422. The proposal served comes
from the campaign's own state and pinned origin, never from the request body, so words in
an objective can't steer it. A key reused with another scenario is a 409.

`--scripted` drops `MODEL_API_KEY` and `BASETEN_API_KEY` from the process before anything
reads them, so it holds no key, even to redact.

Every campaign is labelled. `inference` appears on `CampaignView`, `EventPage`,
`ExperimentView`, `RealityDiffView`, `RunView`, `CapsuleInfo`, `ReplayResult` and
`ApprovalView`. It is pinned at start in a project artifact, `<campaign_id>-origin`, with
the scenario, so no later server can relabel a campaign and a recovered one keeps its
scenario. The pin is written before the campaign's first checkpoint, so every campaign
started from here on has one. If that checkpoint then fails, the pin alone remains and
still fixes the key's scenario. A campaign with no pin, from before this order, reads
`unrecorded`, or `scripted` if its pinned endpoint says so, never the reading server's
mode. A scripted server won't guess its scenario: a resume, or the resume after a decision,
is refused with `settings_changed`, and only `cancel` still works, because stopping serves
no proposal. `inference` is null on an imported capsule and on
a replay not tied to a campaign, because nothing vouches for their origin. Capsule bytes
are unchanged and carry no label: they hold no model output.

**`model_calls` on a scripted campaign.** `record.usage.model_calls` is M05's count of
provider attempts, so under `scripted` or `fixture` it counts checked-in replies. No model
ran. An interface should show it as replies under those labels.

`tests/api/fixture_server.py` serves the same API with `inference: "fixture"`, for tests.
Both labels mean checked-in replies, not a model, and an interface must show them.

## Validation

See the PR description for commands and actual results. Tests use real M04 SQLite
stores, the real M01 adapter over `httpx.MockTransport` fixtures, the real worlds,
verifier, approvals and capsules, and HTTP through the real middleware and worker
threads. No test makes a network request or calls a model.

## Gaps and requests

Deployment gates, all open:

- Production authentication and a real `SessionAdapter`.
- Membership-backed `ApproverAuthority` and production world bindings.
- Multi-process workers: the job registry is in memory, SQLite is single-coordinator, and
  the root lock refuses a second server.
- A live M01 compatibility report before any `LiveInferenceAuthorization`.

To M05 (each is small, and none blocks this branch):

1. `Services.on_node` is documented as test fault injection, and M07 relies on it to know
   the first checkpoint exists and to stop at shutdown. `PinningController` overrides the
   private `_invoke`, the only point after `start`'s gates and before its first checkpoint.
   Either bless both or split `create()` from `run()` and accept a stop signal distinct
   from cancel.
2. `capsule_exported` and `replay_completed` are contract event kinds that nothing emits,
   so capsule actions aren't in the event log.
3. An exception escaping `graph.invoke` (`ApprovalDenied` in `_request_repair`,
   `CampaignSettingsChanged` in a node) leaves the checkpoint `running`. M07 shows it as
   `stalled` with `job.error`; a terminal status would be better.
4. `record()` needs a registered driver, so a campaign whose world stops being runnable
   reads as a 403 rather than a record.

To M06: a public way to ask whether `decide` would accept a principal. `can_approve` reads
`ApprovalService._local_dev_mode` to match it.

To M04:

1. List approvals by project and status: a reviewer can't discover pending approvals, and
   gets an id from its owner or a campaign view.
2. List campaigns by project and owner: a client must keep its campaign ids, or re-send
   its create request.
3. Persist events and tasks; they live in graph state, so reads go through a checkpoint.

To M00:

1. Contracts for the replay result, the repair assessment and coverage, which M07 defines
   today.
2. `GHOSTLAB_AUTH_MODE` and `GHOSTLAB_DEPLOYMENT` in `.env.example`.
3. `src/ghostlab/api/openapi.v1.json text eol=lf` in `.gitattributes`. The drift check
   normalizes line endings until then.
4. M07 needs both the `service` and `orchestration` extras. A combined extra would say so.

To M08: reach the API through a same-origin proxy, generate types from
`openapi.v1.json`, and show `auth_mode`, `production_authenticated` and `inference`. The
document embeds no examples; M00's published specs and submission are instead driven
through the real routes by a test.

Not added: other worlds, the model-driven Analyst, a campaign list route and event
streaming. Polling is the event interface, and no model-token streaming is assumed.
