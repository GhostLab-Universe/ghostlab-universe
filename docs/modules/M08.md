# M08 — Interface

Campaign, evidence, Reality Diff, approval and capsule views over M07's published
contract. React, Vite and TypeScript; no other UI framework.

**Base:** `architecture-and-refund-core` at `24942bd`. M07, M05 and their dependencies
are not in that base yet, so this branch consumes M07's contract by copying it, not by
merging it.

**Status: views and API client complete. Not yet run in a browser.** Results below are
separated by what they prove. Nothing here used a live model or real payments.

## Running it

From `web/`, with the current dependencies. `package.json` has no scripts for these, so
the commands call the tools directly.

```text
./node_modules/.bin/tsc -p tsconfig.json            # strict check of src
./node_modules/.bin/tsc -p tsconfig.tests.json      # strict check of src and tests
./node_modules/.bin/vite build                      # production build: talks to M07
./node_modules/.bin/vite build --mode fixture       # test-data build
./node_modules/.bin/vite --mode fixture             # interface over test data
node tests/run.mjs                                  # generated types, unit, render tests
```

Against a service, run M07 from its checkout, then point the dev proxy at it:

```text
GHOSTLAB_AUTH_MODE=local_dev python tests/api/fixture_server.py --root <dir> --port 8788
GHOSTLAB_API_ORIGIN=http://127.0.0.1:8788 ./node_modules/.bin/vite
M07_ORIGIN=http://127.0.0.1:8788 node tests/integration/run.mjs
```

`GHOSTLAB_API_ORIGIN` defaults to `http://127.0.0.1:8787`, M07's local server. M07 sends
no CORS headers and accepts loopback peers, hosts and origins only, so the browser reaches
it through this same-origin proxy.

The HTML entry is `web/src/index.html`, and Vite's root is `web/src`, because M08 owns
`web/src` and not `web/`.

## How it decides what to show

**Status comes only from an authoritative read.** `ExperimentEvent` has no status field
and its summary is untrusted text, so `logic/live.ts` never derives status from an event.
Each poll reads the campaign first, then any events `event_count` says exist. Every read
is numbered: a response older than the newest applied, or sent before the connection
dropped, is ignored, and a lower `event_count` is never applied over a higher one.
Reading resumes from the cursor, so a reconnect loses nothing and duplicates nothing.

**Success needs agreement.** `logic/repair.ts` shows success only if `verified` is true,
the outcome is `repair_verified`, `run_status` is `completed` and `safety_held` is true. A
`completed` campaign is shown as "Stopped: completed" in a neutral tone, because
`repair_rejected` and `no_failure_found` also end that way. `repair_incomplete` is never
shown as success, even though safety held. A record that disagrees with itself is shown
as inconsistent. Fields are shown as recorded, and an unset `held_by` says why.

**Nothing is computed that could read as a verdict.** Ledger totals and metrics are the
recorded ones. `logic/stateDiff.ts` compares two records to point at the evidence: at the
journey's first divergence the request and outcome match and only `sharing` and
`permission_timeline` differ, so a reader needs that pointer. The page says it does not
judge either side. A reproduced replay with failing checks is "Failure reproduced".

**Approvals are bound.** `logic/approval.ts` builds the body from the request's id and
digest plus the decision and reason. There is no role, approver or scope field. Controls
follow the service's `effective_status`. After any decision the page re-reads the service
rather than trusting the response. Each exact body keeps one `Idempotency-Key`, so a
retry can't decide twice. `can_approve: false` closes the form with an explanation, and
the service still decides. If the service returns no action, the page says not to approve
and the buttons stay disabled.

**Test data is structural.** Every result carries its origins. A fixture build always
shows a banner that can't be dismissed, and each section names its sources. A normal
build contains no fixture data (`synthetic-order-1` and `fx-refund` both have 0 hits in
the built JS). In API mode the page shows the session's `auth_mode`,
`production_authenticated` and `inference`, and says so when inference is scripted.

No credential or provider call exists in the browser. Requests are same-origin, and the
Content-Security-Policy limits `connect-src` to the page's origin.

## Fixture sources

Scenarios live in `src/fixtures/scenarios.ts`, and each names its sources on screen.

| Data | Source |
| --- | --- |
| Diffs, fork runs, proposals, capsules, campaign records, approval request | Published M00 examples |
| Baseline runs, verifier findings, repair records, bound actions and digests, replay results | `src/fixtures/recorded.generated.ts`: real output of the checked-in worlds, verifier, capsule replay and M05's drivers at `4501fa4`, from `tests/fixtures/record_core_outputs.py` |
| Task lists, event lists, campaign states, error scenarios | Hand-authored in M05's shape |

The repair records' `campaign_status` and `outcome` follow `Controller._repair_verdict`,
reimplemented in the recorder. The integration suite checks real ones. The published
journey fork used `max_tool_calls: 40`; the recorded repairs and action use the runnable
20, so that scenario's digest does not bind the published fork's scenario exactly.

## Gaps

- **No browser has run this.** Keyboard use and narrow layouts are implemented with
  native links, buttons and form controls and a stacking layout, and are unverified.
  There are no screenshots. `tests/browser` is ready and needs `@playwright/test`.
- The `react-stopgap.d.ts` and `tests/stopgap.d.ts` declarations stand in for missing type
  packages.
- `configured_tokens` can't work from a browser: it needs a bearer token, and this UI holds
  no credentials. `local_dev` is the only session a browser can use today.
- No campaign or approval list exists in M07, so campaigns open by id and the URL is the
  only memory of one.
- `import`, `replay by id` and a capsule event log are not surfaced. M05 emits neither
  `capsule_exported` nor `replay_completed`, so capsule actions never appear in events.
- M07 reports that `record()` can show a running graph as `awaiting_approval`. The UI
  shows the recorded status and only links to an approval that exists.
- `repair_did_not_hold` and a finished run that attempted nothing have no recorded
  fixture; only the presenter's unit tests cover them.
- Polling is the event transport, so a tool event appears up to 2 seconds late. A campaign
  with more than 5,000 unread events needs another poll to catch up.

## Rejected

- **Reading status from `campaign_status_changed` events.** They carry no status field,
  and parsing an untrusted summary would let text change what is shown.
- **`pending.ts` with hand-written repair and replay types.** It was planned until M07
  published `RepairView` and `ReplayResult`.
- **A second `RealityDiff` view for refund.** M07 maps refund onto the world contracts,
  so one view serves both worlds.
- **Disabling Approve by the browser's clock.** `effective_status` is the service's.
- **Fixtures in the production bundle.** They would have to be excluded by care, not by
  construction.
