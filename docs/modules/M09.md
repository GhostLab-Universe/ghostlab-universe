## Telemetry interface

Standard library only, so importing it loads no Pydantic, httpx or LangGraph (tested in a
subprocess). M09 instruments no other package: each owner injects a `Telemetry` and
writes against it. `NULL_TELEMETRY` is a safe default that records nothing.

```python
telemetry = Telemetry(FileSink(path, max_bytes=8_000_000), clock=clock)
context = TraceContext(trace_id=state["trace_id"], project_id=project, campaign_id=campaign,
                       versions=Versions(workflow_version="ghostlab-orchestration/2"))
with telemetry.span("model.call", context.with_task(task_id), role="explorer") as span:
    span.usage = Usage.from_mapping(reply["usage"])  # a missing value stays None
    span.attempt, span.outcome = 1, reply["status"]
telemetry.event("approval.requested", context, approval_id=approval_id,
                approval_status="pending")
```

Use the campaign's own `trace_id`, which is stable across a restart. The context is
passed explicitly rather than held in a context variable, because the controller runs
baseline and fork on worker threads.

### Record fields (`ghostlab-telemetry/1`)

A record is closed: `validate_record` rejects unknown fields, and a new field is a
schema change. Events and spans share one shape. `None`/`null` always means unknown or
not applicable.

| Field | Type | Meaning |
| --- | --- | --- |
| `schema` | `ghostlab-telemetry/1` | Version of this shape |
| `kind` | `event` \| `span` | A point in time, or a timed scope |
| `name` | dotted lowercase | See `EVENT_NAMES`; any matching name is accepted |
| `timestamp` | RFC 3339 UTC | When written (a span's end) |
| `started_at` | RFC 3339 UTC \| null | Spans only |
| `trace_id` | 32 hex | The campaign's W3C-shaped trace id |
| `span_id` | 16 hex | This record |
| `parent_span_id` | 16 hex \| null | Parent trace id for nesting |
| `project_id`, `campaign_id`, `task_id` | text \| null | Ownership and position |
| `role`, `provider`, `model` | text \| null | Who did the work |
| `prompt_version`, `skill_id`, `skill_version`, `workflow_version`, `world_version` | text \| null | What it ran |
| `latency_ms` | int \| null | Measured by the injected timer for spans |
| `usage` | object | `input_tokens`, `output_tokens`, `cost_minor`, `cost_currency`, each nullable |
| `attempt`, `retries` | int \| null | Retry position and count |
| `cancelled` | bool \| null | Cancellation |
| `validation_failures` | int \| null | Rejected model or tool output |
| `approval_id`, `approval_status` | text \| null | `pending`, `approved`, `rejected`, `expired`, `consumed` or `denied` |
| `outcome`, `error_code` | text \| null | Result, and M00's `ErrorCode` where there is one |
| `attributes` | flat object | Allowlisted scalars only |
| `dropped_attributes` | int | How many attributes were refused |

### What can't be recorded

Redaction is deny-by-default, on top of M06's `Redactor`, which isn't copied:

- There's no field for a prompt, reply, tool argument, customer record or free text.
  Evidence is referenced by id or digest.
- Attributes survive only if the name is in `ATTRIBUTE_ALLOWLIST` (or was added at
  construction, where a secret-looking name is refused) and the value is a scalar.
  Everything else is dropped and counted.
- Text must be identifier-shaped. Free text is replaced whole, not scrubbed. So are long
  opaque runs and common credential shapes that M06's patterns don't name. Digests stay.
- An exception's message is never recorded. A span records `outcome: error` and the
  exception's class name in the `error_class` attribute.
- If a record can't be sanitized, it's dropped and counted. It's never written raw.
- A sink failure is counted and never reaches the business path.

### Sinks and the export boundary

| Sink | Bound | Notes |
| --- | --- | --- |
| `InMemorySink` | `max_events` (10,000), newest kept | `dropped` counts evictions |
| `FileSink` | Each file at most `max_bytes` (8 MiB); at most `max_bytes × (backups + 1)` | JSON Lines. Checked before each write. Rotates; with `backups=0` it drops new records. `dropped` counts |
| `FanOutSink` | none of its own | One failing sink doesn't stop the others |
| `OtlpExportSink` | `max_buffer` (4,096) | Hands OTLP/JSON batches to an injected `SpanExporter` |

`to_otlp` is a pure mapping to the OTLP/JSON trace shape. There's no SDK, no exporter and
no connection. OTLP has no null, so unknown usage is omitted, never sent as 0, and
`ghostlab.usage.unknown` names what was unknown. The `gen_ai.*` attribute names follow
OpenTelemetry's GenAI conventions, which are still in development, and this mapping
hasn't been tried against a live collector.

### Retention and access

| What | Kept for | Access | Enforcement |
| --- | --- | --- | --- |
| Local telemetry files | 30 days after the last write, and at most the sink's byte bound | The operator's user account | **Byte bound: code** (`FileSink`). **Age: code, when called** (`prune_expired`); nothing schedules it yet. Moving a file out of the sink is the audit hold |
| POSIX file modes | n/a | Files `0600`, directory `0700` | **Code**, on creation |
| Windows ACLs | n/a | The directory must not grant other users access | **Documented only.** Modes don't apply on Windows; files inherit the directory's ACL |
| Telemetry across projects | n/a | A reader sees only its own `project_id` | **Documented only.** Records carry `project_id`, but no authenticated reader exists until M07 |
| In-memory records | Process lifetime, at most `max_events` | Same process | **Code** |
| Exported spans | Whatever the collector keeps | The collector's operator | **Documented only.** No exporter ships. Enabling one is a reviewed deployment change, and retention there must be recorded in that change |
| Evidence (runs, capsules, findings) | Per M04's retention, not telemetry's | Project-owned artifacts | M04 |

Telemetry is operational evidence, not the audit of record: pass or fail comes from
stored runs and verifiers, and deleting telemetry changes no verdict.

### Tracing a campaign today

No package writes telemetry yet, because each owner adds that. Until then,
`emit_campaign_trace` rebuilds a trace from `controller.state()`, plus the ledger totals
and HTTP attempts when they're available:

- It reads structured fields only. Event summaries and error messages are skipped, because
  they can quote model output.
- Ids are derived, so rebuilding a campaign gives the same trace.
- Tasks, errors and HTTP attempts have no stored time, so they carry the campaign's last
  recorded time, and `latency_ms` is null. Per-call timing needs M05 and M01 to write
  spans as they run.

## Independent evaluations (`ghostlab-evaluation/1`)

```sh
python -m evals.run --out <dir>      # run, store evidence, score, gate; exit 1 blocks
python -m evals.gate <dir>           # rescore stored evidence only
python -m evals.release --report <dir>/report.json --commit <sha>
```

| Step | Module | Reads |
| --- | --- | --- |
| Run | `evals/cases.py`, `evals/harness.py` | Drives the real controller, M04 SQLite stores, M01 adapter, M03 context, M06 policy and M02 worlds. Only the HTTP transport is mocked, with labeled fixtures |
| Record | `evals/evidence.py` | Copies what the campaign left behind into `<dir>/evidence/<case>.json`, reading runs through the M04 artifact store, and writes a trace to `<dir>/telemetry/` |
| Judge | `evals/oracles.py` | Recomputes each verdict from stored runs. Shares no code with M02's verifiers, M06's guard or M05's findings |
| Score | `evals/score.py` | Files only. It can't reach a controller, a store or a model |
| Gate | `evals/gate.py` | Compares the report with the reviewed `evals/expected.json` |

A case's harness is separate from M05's on purpose, and the cases assert outcomes from
evidence rather than repeating M05's unit checks. Every case also gets these checks:

| Common expectation | Meaning |
| --- | --- |
| `evidence_digests_match` | Each stored run still hashes to its recorded digest |
| `findings_match_the_independent_oracle` | The controller's findings agree with the oracle, so a claim can't overrule evidence |
| `coverage_matches_the_stored_runs` | Each experiment's recorded `coverage` says what its stored runs say |
| `no_secret_in_stores` | Every byte of every SQLite file and artifact was searched for the fixture credential and the synthetic secret |
| `no_secret_in_evidence`, `no_secret_in_telemetry` | The same, for what the suite produced |
| `trace_valid_and_complete` | Each campaign has a valid trace with one root span |

An adversarial fixture stands in for a model that obeyed the attack. Nothing here
measures how a real model behaves.

### Report shape

| Field | Meaning |
| --- | --- |
| `schema` | `ghostlab-evaluation/1` |
| `inference`, `live_provider_contacted`, `fixture_label` | Always `mocked`, `false` and the fixture label. The gate refuses anything else |
| `environment` | Python version and platform |
| `aggregate` | Totals, plus `by_category`. Each rate carries its numerator and denominator |
| `cases[]` | `case_id`, `category`, `world`, `status`, `failed_expectations`, `expectations`, `metrics`, `telemetry_records`, `local_wall_ms`, `fingerprint` |
| `deferred[]` | What wasn't measured, and why |

`fingerprint` holds everything deterministic: outcomes, task states, error codes, run
digests, HTTP statuses, measurements and metrics. Local wall time stays out of it.

| Metric | Definition |
| --- | --- |
| Tool success | Trace events without an error, over all events. An injected fault or a guard denial counts as a failure, and both are also reported separately |
| Handoff failures | Tasks with a dependency that ended skipped, failed or cancelled, over all tasks with one |
| Recovery | Recoveries that reached the required result, over recoveries attempted |
| Human correction | Approval decisions recorded, how many were rejections, and how many are still pending |
| Latency | `provider_ms` is null, because no provider was contacted. `local_wall_ms` is this machine running fixtures |
| Cost per successful task | Null. No price is verified, and the ledger records no cost |
| Fixture tokens | Ledger totals of fixture usage (700 in, 120 out per reply). They describe the fixture, not a model |

The random, one-pass and adaptive comparison is **deferred**. Inference is scripted, so
there's nothing to sample, and no result is claimed.

## CI

`.github/workflows/ci.yml` runs on pull requests and on pushes to `main` and
`architecture-and-refund-core`:

| Job | Runs |
| --- | --- |
| `core-bare` | The 14 core tests, with no packages installed |
| `python` | `uv lock --check`, locked sync, full pytest with warnings as errors, `export --check`, on Ubuntu and Windows |
| `demos` | Refund and journey demo and replay |
| `contracts-ts` | `npm ci`, `contracts:verify`, `contracts:typecheck`, on the `.nvmrc` Node |
| `evaluations` | `python -m evals.run`, keeping the evidence for 30 days |
| `promotion-gate` | Fails unless every job above succeeded |

It holds no credentials, has read-only access, and doesn't deploy or merge. uv is pinned
to 0.13.6, and actions are pinned to the commits their release tags pointed to on
2026-10-30 (read with `git ls-remote`).

**This workflow has not run on GitHub.** Not verified:

- that GitHub accepts the file, or that the pinned actions run as written;
- that evaluation digests match on Linux, where they should be identical because they're
  computed from canonical JSON, though that's unproven until the first run;
- the `core-bare` step on a runner (it passed locally with uv 0.13.6 on Windows);
- that `promotion-gate` actually blocks anything. It must be made a required status check
  by a repository admin, and until then the block is procedural.

| Status | Value | What can change it |

`promotable` is about offline promotion only. Customer-connected use is decided
separately, and a status in the targets file is treated as a claim:

| Needed for `customer_connected_use_allowed` | Why |
| --- | --- |
| `release_target.kind` is `customer_connected` | A local target is always false, whatever else the record says |
| Runtime status `authenticated_service` | No authenticated service exists yet |
| Every gate in `security_gates`, gates 1 to 4 of `docs/acceptance-gates.md`, marked `passed` with an evidence file | A gate's file proves only that evidence was named; a human still reviews it |
| A compatibility report that exists inside the release root and passes `LiveInferenceAuthorization.check` | The same check the controller applies before a paid call, bound to the claimed provider, endpoint, model and spending cap, and run for every runnable world's output schema. It must also hold no secret |
| No offline blocker | A release that can't be promoted can't be connected |

The record says `live_evidence.validated`, so a claimed `passed` is never shown as proven.
`customer_connected_blockers` lists what's missing. A live claim doesn't affect
`promotable`, in either direction.

A regression blocks in three places, all tested: `evals.run` and `evals.gate` exit 1,
`build_record` returns `promotable: false`, and the CI job fails. Two tests break real
behaviour instead of editing a file: one sends the repaired adapter back to retrying, and
one runs the repair unguarded. Both are caught.
